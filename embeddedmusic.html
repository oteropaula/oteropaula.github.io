Wireless Embedded
Musical Generator

A dual-microcontroller embedded system for real-time melody creation, storage and remote playback. An Arduino Mega 2560 handles physical interaction via rotary encoder and RGB LCD display, while an ESP32 hosts a WiFi access point and a web server that lets users select and play stored melodies from any browser on the network.

Course Embedded Systems - BSc Digital & Multimedia Technology
Hardware Arduino Mega 2560 · ESP32-DevKitV1
Institution UPV - ETSI Telecomunicación

Overview

Two microcontrollers, one instrument

The system lets a user create custom melodies using a rotary encoder and a buzzer on the Arduino side, then select and play them remotely through a browser-based web interface served by the ESP32 over its own WiFi access point. The two boards communicate bidirectionally over UART - the Arduino sends newly created melody names to the ESP32, and the ESP32 sends play commands back to the Arduino when a user clicks a melody in the web UI.

The web server's HTML, icon and image assets are stored in the ESP32's flash using SPIFFS (Serial Peripheral Interface Flash File System), served directly to connected browsers without any external hosting.

Hardware setup - wiring diagram

Arduino Mega 2560 connected to rotary encoder (CLK pin 2, DT pin 3, SW pin 4), RGB LCD display, and buzzer (pin 8). ESP32-DevKitV1 connected via UART on Serial1 / Serial2 at 115200 baud.

Component - Arduino Mega 2560 (melodies.ino)

Creating and playing melodies

The Arduino code manages the full melody creation workflow through a single rotary encoder and its push-button switch. Turning the encoder scrolls through eight available notes (DO, RE, MI, FA, SOL, LA, SI, DO); the LCD shows the currently selected note in real time. The switch button handles all editing actions through a multi-tap detection system with debounce logic.

1️⃣

1 press - Add note

Appends the currently selected note (250 ms duration) to the melody being composed. The LCD updates with the current note count.

2️⃣

2 presses - Save melody

Saves the composed melody with an auto-generated name (melodia1, melodia2, …). The user is then asked via encoder whether to create another melody or stop. The melody name is sent to the ESP32 over Serial1 with the M: prefix protocol.

3️⃣

3 presses - Delete last note

Removes the most recently added note from the current melody and decrements the note counter displayed on the LCD.

4️⃣

4 presses - Clear all notes

Resets the current melody to zero notes, letting the user start the composition over from scratch without saving.

🎵

Remote playback via UART

When the ESP32 forwards a play command (M:melodyName) over Serial1, the Arduino looks up the melody by name - first in predefined melodies, then in user-created ones - and plays each note on the buzzer using the tone() function at the specified frequency and duration.

Component - ESP32-DevKitV1 (wifi.ino)

WiFi access point & web server

The ESP32 creates its own WiFi access point (SSID: ESP32-AP04) rather than joining an existing network. Any device that connects to it can open the web interface in a browser. The web server runs on port 80 and serves all resources from SPIFFS - the HTML page, an icon, and a decorative image are all stored in the ESP32's flash and served with correct MIME types.

The melody list on the web page auto-refreshes every 5 seconds via a JavaScript setTimeout loop, so newly created melodies appear without the user needing to reload the page. When a melody is clicked, the JavaScript sends a GET /play?melody=name request; the server strips whitespace, forwards the name to the Arduino over Serial2 with the M: prefix, and sets a melodyPlaying flag with a short delay to prevent duplicate playback.

Route - /

handleRoot()

Opens index.html from SPIFFS and streams it to the browser. Returns HTTP 500 if the file cannot be opened.

Route - /melodies

handleMelodies()

Builds an HTML list of all predefined melodies (A–D) and all user-created ones stored in createdMelodies[]. Returned as plain text; injected into the page by JavaScript.

Route - /play

handlePlay()

Receives melody name as a query parameter, trims whitespace, forwards via Serial2.println("M:" + name) to the Arduino. Uses melodyPlaying flag to block duplicate requests.

Routes - /icono.jpg · /image.png

handleIcon() / handleImage()

Streams static assets from SPIFFS with the correct MIME type (image/jpg, image/png). Returns HTTP 404 if not found.

The loop() function also listens on Serial2 for incoming M: messages from the Arduino - when a new melody is created and saved, the Arduino sends its name, and the ESP32 stores it in the createdMelodies[] array (up to 10 entries). This is what makes the dynamically updated melody list in the web UI work.

SPIFFS setup

Serving the web UI from flash

Rather than embedding HTML as a string in the C++ source, the web UI is stored as a separate file in the ESP32's flash filesystem using SPIFFS. The deployment process involves running a custom deploy_spiffs.bat script (provided by the course) that uses mkspiffs and esptool to pack the data/ folder contents into a spiffs.bin binary and flash it to the device. The data/ folder contains index.html, icono.jpg, and image.png.

This separation means the web UI can be edited and reflashed independently of the firmware - a clean architectural boundary that also keeps the Arduino sketch readable.

Engineering challenges

Problems encountered & how we solved them

Problem

Melodies selected in the browser weren't reaching the Arduino - no playback triggered.

Solution

Both sides were missing the correct serial port initialisation. Added Serial1.begin(115200) on the Arduino side and Serial2.begin(115200) on the ESP32 side to establish the UART link.

Problem

Every melody played twice in succession - the buzzer reproduced the same piece back-to-back.

Solution

The melody name was being sent twice by the ESP32. Added a melodyPlaying boolean flag: set to true on play, a short delay(1000), then back to false. Subsequent requests are rejected while the flag is active.

Problem

LCD showed ghost characters - scrolling past "SOL" left the trailing "L" on screen; confirmation brackets displayed as "[Si] [No" instead of "[Si] No".

Solution

Added lcd.print(" ") (spaces) before each display update to overwrite the previous content, effectively clearing residual characters without calling lcd.clear() for the whole screen.

Problem

When deleting all notes with currentNoteIndex ≥ 10, the second digit of the count remained on the LCD.

Solution

Extended the whitespace-clearing approach to cover the extra character position for two-digit numbers, ensuring both digits were wiped before the new count was printed.

Problem

Created melody name was not being sent to the ESP32 - only an empty character arrived.

Solution

The variable holding the melody name was being defined after currentMelodyIndex was incremented, capturing the wrong slot. Moving the variable definition to immediately after the name assignment fixed the ordering issue.

Problem

Rotary encoder presses were frequently misdetected - double-counts or missed taps because the user had to press very fast.

Solution

Added delay() calls at key points and a debounceTime variable (200 ms) checked via millis() to give the encoder time to settle between transitions.

Problem

SPIFFS deployment script failed: MKSPIFFS, ESPTOOL and PARTITION_FILE paths were wrong for the local Arduino IDE installation version.

Solution

Updated all three paths in the .bat script to match the installed versions. Additionally, the script must be run with Arduino IDE fully closed - the IDE holds the serial port open, blocking the flash operation.

Reflection

What we learned

The most valuable lesson from this project was understanding the full stack of an embedded IoT system - from raw hardware signals (encoder pulses, buzzer tones) up through UART communication, WiFi networking, and a browser-facing HTTP server. Each layer introduced its own failure modes, and debugging required reasoning about multiple systems at once rather than a single codebase.

Working without the planned course practice on SPIFFS and WiFi meant we had to read documentation and source examples independently, which made the learning more durable. The ghost-character LCD problems in particular were a good reminder that embedded displays have no concept of "refresh" - every pixel state must be managed explicitly in code.

The dual-serial-port approach (Serial1 on Arduino, Serial2 on ESP32 for the same UART line) is a pattern worth knowing: it keeps the debug console (Serial) free while dedicating a hardware UART to inter-device communication.
